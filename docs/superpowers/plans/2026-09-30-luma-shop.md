# Luma Shop Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add the approved Luma tech-shop demo after Donewell, with database-backed guest carts, Google sign-in at checkout, atomic simulated orders, and Mailgun confirmations.

**Architecture:** Keep the Vite multi-page site and vanilla JavaScript. Supabase provides anonymous/permanent sessions, Postgres records, Storage assets, authenticated Edge Functions, and scheduled jobs. Server transactions own cart changes, cart transfer, order totals, and order creation; Mailgun sending happens separately through an outbox worker.

**Tech Stack:** Existing Vite/Tailwind/Playwright, pinned `@supabase/supabase-js`, Deno Edge Functions, a pinned Postgres driver, Supabase Postgres/Auth/Storage/Cron, Google OAuth, Mailgun HTTP API. Use Node's built-in test runner for browser-module logic, Deno tests for server logic, and SQL integration tests against an isolated local database.

**Spec:** [Luma design specification](../specs/2026-09-30-luma-shop-design.md). The user subsequently approved implementation and subagents.

**Implementation checkpoint:** Storefront/direct routes, anonymous-cart modules, Google handoff recovery, simulated checkout/receipt/history, SQL schema/catalog, and six server functions are implemented. Additive schema and functions are deployed to the isolated Luma project. Provider secrets, Auth configuration, scheduler activation, and Storage uploads remain operator setup; live Google/order/Mailgun and concurrent service integration checks are pending. Anonymous account deletion was rejected by automatic approval review and is isolated in `supabase/pending-migrations/`, outside normal deployment. See `docs/luma-operations.md` for exact setup and verification limits. Checkbox steps below describe the original complete-release plan; this checkpoint does not claim a public rollout is ready.

## Global Constraints

- Node.js 22 or newer (pinned Supabase client requirement); retain semantic HTML, vanilla JavaScript modules, Tailwind, and `src/index.css`. No React migration or client router.
- Luma is project `02 / Commerce` after Donewell; follow approved Prism Playground draft `915202d9-2dce-46dc-9f3d-83a65613918d`, version 2.
- Guests can add, edit, remove, and view carts without a Google sign-in prompt. Checkout requires a permanent Google user with confirmed email.
- Supabase is authoritative for shop business records, including guest carts. Guest recovery requires the original browser session; account carts support cross-device recovery.
- Preserve `donewell-tasks-v1`, backup version `1`, and all existing Donewell controls. Scope shop styles and behavior to Luma.
- Money is integer kobo, currency `NGN`, delivery fee `250000` kobo, with no separate tax calculation or real payment.
- Quantities are `1–10`; at most `20` distinct cart lines. Seed seven products at the exact illustrative prices in the spec.
- Handoff tokens have `256` random bits, expire after `15` minutes, and are stored only as hashes server-side; no tokens in URLs/logs.
- New orders are limited to `3` per hour and `10` per day per permanent user. Idempotent retries do not count as new orders.
- Email retries follow the initial attempt after `1`, `5`, and `30` minutes. Worker runs every minute; delivery is at-least-once, not exactly-once.
- Clean abandoned anonymous carts/users after `30` days of cart inactivity; purge expired handoffs after `24` hours; preserve active transfer leases and permanent accounts.
- Exact disclosure: “Portfolio demo — no payment or shipment.” No cards, shipping promises, fabricated ratings, or marketing email.
- Validate desktop and `320px`/`390px` widths, keyboard interaction, reduced motion, and WCAG AA contrast.
- Never put Mailgun keys, privileged database credentials, Google secrets, or recovery sessions into public artifacts. Pin new dependencies and commit lockfiles.
- Run the full `npm test` suite after shared CSS/page changes, regenerate tracked `dist/`, and update AGENTS.md for actual architecture/workflow changes.

## Review Focus

1. Two tabs editing one cart: reject stale revisions without silently losing changes; covered by Task 3's concurrent-update test.
2. The Google callback is reloaded after a successful transfer: restore the same result rather than adding quantities again; covered by Task 4's replay test.
3. A user signs out on a shared device: hide all former-account records and start a fresh guest cart; covered by Task 4's sign-out test.
4. A product changes price after review: require renewed customer review, never place an order at an unseen total; covered by Task 5's quote-change test.
5. The email worker crashes after provider acceptance: preserve the order and recover the lease, while documenting possible duplicate mail; covered by Task 6's crash-recovery test.

## Shared contracts

Define these names in `src/shop/contracts.js` as JSDoc types/constants and mirror their JSON fields in server TypeScript types; no runtime cross-environment imports.

- `Product`: `{id, slug, name, description, categorySlug, specifications, images:[{url,alt}], variants:[{id,label,priceKobo,currency,active}]}`.
- `Cart`: `{id, revision, lines:[{variantId,productName,variantLabel,priceKobo,quantity,active}], subtotalKobo}`. An empty cart is a valid state.
- `Quote`: `{cartId, cartRevision, fingerprint, subtotalKobo, deliveryKobo, totalKobo, currency:'NGN'}`.
- `Order`: `{id, reference, createdAt, demo:true, status:'confirmed', items, subtotalKobo, deliveryKobo, totalKobo, currency:'NGN', emailStatus}`.
- Mutation request: `{variantId, quantity, expectedRevision}`; quantity `0` means remove. Server validates the resulting cart bounds.
- Checkout request: `{idempotencyKey, cartRevision, quoteFingerprint, delivery:{recipientName,city,address}}`. Recipient email, user id, prices, and fees are server-derived.
- Errors: `{error:{code,message,details?}}`; codes include `AUTH_REQUIRED`, `PERMANENT_ACCOUNT_REQUIRED`, `CART_CONFLICT`, `MERGE_CONFLICT`, `QUOTE_CHANGED`, `ITEM_UNAVAILABLE`, `RATE_LIMITED`, `HANDOFF_EXPIRED`, `HANDOFF_USED`, and `VALIDATION_FAILED`. Use `401` for invalid sessions, `403` for disallowed identity, `409` for conflicts, `422` for invalid content, `429` for limits.
- Browser API functions: `getCart(): Promise<Cart>`, `updateCart(input): Promise<Cart>`, `prepareHandoff(): Promise<{token,expiresAt}>`, `redeemHandoff(token): Promise<Cart>`, `getQuote(): Promise<Quote>`, `placeOrder(input): Promise<Order>`, `getOrder(id): Promise<Order>`, `listOrders(): Promise<Order[]>`.

## Migration, release, and rollback

- Use CLI-generated migration filenames only. Iterate in the isolated database, run advisors, then generate/review migration history using the installed CLI's documented workflow. Migrations must replay cleanly with seeds on an empty test project.
- Apply schema/functions to staging first; use separate keys/Google redirects/Mailgun configuration for the public demo. Never point SQL tests or cleanup at an unrelated project.
- Public release requires all functional checks and actual selected service configuration. An unavailable integration must appear as unavailable; no fallback to fake persisted orders or hardcoded working claims.
- Frontend rollback restores the prior Vercel deployment/source build and removes Luma initialization while retaining Donewell local data. Disable new schedules/Edge Function access before disabling the shop backend. Preserve order/email records and take a database backup before any destructive rollback; prefer leaving unused additive tables over dropping customer records.
- Pause email sending before retrying a deployment with uncertain job state; retain idempotency/job history. Rotate leaked credentials through provider secret stores and rebuild any accidentally exposed client asset.
